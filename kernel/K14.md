## 2. Local patches N1-N3 and their review against mainline v7.3

Mainline reference: `torvalds/linux.git` tag `v7.3` (`091b06388b11`), shallow fetch. Line numbers below are v7.3
unless they say 6.18. All three patches also apply unchanged with `git am` to v7.3's `drivers/gpu/drm/nouveau`, so
they forward-port.

### N1: `0101` no `ignore_hotplug` when the bridge has _PR3

**Problem.**

* `nouveau_pmops_runtime_suspend()` calls `pci_ignore_hotplug(pdev)` on every runtime suspend: 6.18
  `nouveau_drm.c:1131`, v7.3 `nouveau_drm.c:1176`, unchanged upstream.
* `pci_ignore_hotplug()` (6.18 `pci.c:6408-6417`, v7.3 `pci.c:6413-6422`) sets the flag on the GPU and on its parent
  bridge. Nothing ever clears it; there are only setters in the tree.
* Its readers are:
  * `pciehp_isr()`, which drops every slot event of that port (6.18 `pciehp_hpc.c:717`, v7.3 `:718`);
  * acpiphp, which treats the device as alive in `trim_stale_devices()` and skips it in slot enable (`acpiphp_glue.c:657`,
    `:581`).
* On the SB3 the GPU is behind the detachable base, so after a single nouveau runtime suspend a later removal is never
  handled. This is plan A6.

**Fix.** Skip `pci_ignore_hotplug()` when `nouveau_pr3_power_managed()` holds. Both of these must be true:

1. The upstream bridge has `bridge_d3` and `pci_pr3_present(bridge)`. This is exactly the predicate nouveau already
   uses to stop using the Optimus _DSM (`nouveau_dsm_pci_probe()`, 6.18 and v7.3 `nouveau_acpi.c:229-230`). In that
   case the PCI core powers the slot down through the port's own runtime PM, not behind its back.
2. The host bridge has `native_pme`, or no `native_pcie_hotplug`.
   * pciehp masks the slot interrupt across the port's D3cold only when the OS owns PME
     (`pciehp_disable_interrupt()`: "Disable hotplug interrupt so that it does not trigger immediately when the
     downstream link goes down", 6.18 `pciehp_core.c:263-271`). It also clears the retraining events on runtime resume
     only then (`:335-347`).
   * Without native PME the link-down would be handled as a surprise removal of a bound GPU, so N1 keeps the old
     behaviour there.
   * Without native PCIe hotplug, pciehp is not bound, and acpiphp only acts on ACPI notifications. acpiphp's
     `trim_stale_devices()` still checks `_STA` and `pci_device_is_present()` before removing anything.
   * `pci_find_host_bridge()` is open-coded (walk to the root bus, then `to_pci_host_bridge()`), because the symbol is
     trimmed from this GKI's exports. Calling it would add an export and break K-03.

A `dev_info_once()` line "runtime PM through ACPI _PR3, hotplug left enabled" makes the active path visible on
hardware.

**Precedent and counter-precedent.**

* amdgpu `ceb4de67c960` ("drm/amdgpu: no need to call pci_ignore_hotplug for _PR3", Alex Deucher, 2020-12-09: "The
  platform knows it's doing d3cold") removed the call for _PR3/BOCO. v7.3 `amdgpu_drv.c:2912-2921` still does
  "nothing to do" for BOCO and calls it only on the ATPX path.
* xe still calls it on its d3cold path (v7.3 `xe_pci.c:1384-1388`; d3cold is gated on `pci_pr3_present(root_pdev)`,
  `xe_pm.c:318`).
* This difference is why N1 also requires native PME. On the SB3, `_OSC` control is a hardware-time check (README HW
  list).

**What N1 does not change.** The `_DSM`/Optimus path, system suspend, and the PCI state handling (nouveau still saves
state and requests D3cold itself). Mainline v7.3 behaves exactly like 6.18 here (plus the GCX readiness check, see N3),
so there is no conflict with a later upstream fix.

### N2: `0102` presence guards

**Problem.** nouveau has no hot-unplug support. If the GPU leaves the bus while runtime suspended:

* The next `nouveau_pmops_runtime_resume()` re-enables the device and calls `nouveau_do_resume()`, which boots GSP-RM
  on absent hardware.
* `pci_device_remove()` does `pm_runtime_get_sync()` before `.remove` (6.18 `pci-driver.c:465-474`), so even the
  remove path triggers that resume.
* The teardown then sends GSP-RM RPCs that can never be answered:
  * `r535_gsp_msgq_wait()` polls a system-memory ring for up to 4,000,000 `usleep_range(1, 2)` iterations per message
    (`r535/rpc.c:458`, unchanged in v7.3) and then `WARN_ON`s;
  * `r535_gsp_cmdq_push()` waits for ring space for up to 1,000,000 iterations (`:360`).
* MMIO polling loops (`nvkm_msec`) are bounded already: on a missing GPU the PTIMER reads back constant, and
  `nvkm_timer_wait_test()` gives up after 16 identical reads.
* Mainline v7.3 has no presence handling in nouveau. The only `pci_device_is_present()` users in `drivers/gpu/drm` are
  amdgpu's resume and runtime resume (`amdgpu_drv.c:2695, :2956`), which set `no_hw_access`.

**Fix.**

* The PCI core powers the device up and restores its config space *before* it calls the driver's runtime_resume
  (6.18 `pci-driver.c:1341-1366`, `pci_pm_default_resume_early()` at `:1353`). After a D3cold exit the bridge's
  resume has already waited for the link (`pci_pm_bridge_power_up_actions()`). So a present GPU answers the
  vendor-id read, and the check cannot misfire on a GPU that is merely powered off. amdgpu makes the same check at
  the same point.
* `nouveau_drm_device_gone()`: PCI devices only. If `pci_device_is_present()` fails, it sets the new
  `nvkm_device.gone` flag, logs once and returns true. It is used in four places:
  * `nouveau_pmops_runtime_resume()`: return `-ENODEV` before any PCI or GSP access. The PM core records
    runtime_error, and later `pm_runtime_get_sync()` calls fail fast.
  * `nouveau_pmops_resume()` (system resume): the same guard. This is an addition to the plan's list, which named only
    runtime resume, remove and fini. A base removed during s2idle would otherwise stall `dpm_resume` behind GSP
    timeouts; amdgpu checks both resume paths too.
  * `nouveau_drm_remove()`: mark the device gone before `nouveau_drm_device_remove()`. That function already calls
    `drm_dev_unplug()` first, then fini.
  * `nouveau_drm_device_fini()`: `pm_runtime_get_noresume()` instead of `pm_runtime_get_sync()` when gone. The
    reference count stays balanced, and the device is never powered up.
* nvkm side:
  * `r535_gsp_msgq_wait()` and the `r535_gsp_cmdq_push()` space wait return `-ENODEV` as soon as `gone` is set. The
    flag is checked inside the loops, so an in-flight wait also ends.
  * `nvkm_gsp_fini()` skips the unload sequence (msleep, unload RPC and the 2 s poll) when gone.
  * The software teardown (clients, TTM, display objects, memory) still runs. Callers already handle RPC errors, the
    same way as for timeouts.

**Deviation: no `drm_dev_unplug()` in the resume callbacks.** The plan says "call `drm_dev_unplug()`" in all three
places. In runtime resume that would deadlock:

* runtime resume can run synchronously inside a `drm_dev_enter()` section, because `nouveau_drm_postclose()` takes
  `drm_dev_enter()` and then `pm_runtime_get_sync()` (k14 tree `nouveau_drm.c:1359-1362`, v7.3 `:1288-1291`);
* `drm_dev_unplug()`'s `synchronize_srcu()` would then wait for its own caller.

The unplug therefore stays where nouveau already has it: first thing in the remove path. Real removals reach that
path either through pciehp/acpiphp (with N1) or through gb_power's PCI remove. In `nouveau_drm_remove()` the plan's
"`drm_dev_unplug()`" is therefore the existing first call of `nouveau_drm_device_remove()`.

**What N2 does not change.** A present device takes exactly the old paths: the only added work is one config-space
vendor-id read per resume, remove and fini. There is still no dummy page for the GEM fault path (plan risk 4).

### N3: `0103` no power-off after a failed runtime suspend

**Problem.**

* `nouveau_pmops_runtime_suspend()` ignores the return value of `nouveau_do_suspend()`. It runs `pci_save_state`,
  `pci_disable_device` and `pci_set_power_state(D3cold)`, then returns the error (6.18 `nouveau_drm.c:1128-1135`; v7.3
  `:1173-1179`, same code).
* `rpm_suspend()` treats any error as "still active", and errors other than -EBUSY/-EAGAIN also set
  `runtime_error` (6.18 `runtime.c:472-473`). Either way the GPU is in D3cold while the PM core believes it is active,
  with VRAM or GSP-RM state possibly unsaved.
* `nouveau_do_suspend()` also ignores `ttm_resource_manager_evict_all()`'s return value (6.18 `:958-961`, v7.3 `:964`).
* Its failure paths leave SVM, dmem and LED suspended; the early display-suspend failure even returns directly.

**Fix.**

* Runtime suspend: if `nouveau_do_suspend()` fails, log with `dev_warn_ratelimited()`, call
  `pm_runtime_mark_last_busy()` and return `-EBUSY` before any PCI power change.
  * `-EBUSY` does not set `runtime_error`.
  * Marking the device busy makes `rpm_suspend()` re-arm the autosuspend timer (`runtime.c:761-762`). The next
    attempt therefore comes one autosuspend delay later, not in a loop.
  * This is the pattern mainline v7.3 itself uses in the same function for its GCX readiness check
    (`nouveau_drm.c:1162-1169`, `cb4c7603678c` series): `pm_runtime_mark_last_busy(dev); return -EBUSY;`.
* The success path now returns 0.
* `nouveau_do_suspend()`:
  * a failed VRAM eviction fails a *runtime* suspend (`goto fail_display`); system suspend keeps its best-effort
    behaviour and only logs;
  * every failure path ends in a new `fail_suspend:` label that runs `nouveau_led_resume()`, `nouveau_dmem_resume()`
    and `nouveau_svm_resume()`, mirroring `nouveau_do_resume()`.

**Notes.**

* `nouveau_switcheroo_optimus_dsm()` still runs before `nouveau_do_suspend()`, as upstream. If the suspend then fails,
  the Optimus power-down stays armed. That is harmless: it only acts on the next D3 transition, which now happens only
  after a successful suspend. On _PR3 platforms (`optimus_skip_dsm`) the call is a no-op anyway.
* A permanently failing suspend keeps the GPU in D0 and retries every 5 s (the autosuspend delay). gb_power's watchdog
  flags "D0 for more than 60 s with refcnt 0" (INTERFACES 10.5), so the condition is visible rather than silent.
* The optional 7.3 GCX series would slot in before the `nouveau_switcheroo_optimus_dsm()` call without conflict.

## 3. Builder workspace and reproducibility

* Branches in `/build/gki/common`:
  * `k13-native` (`8aa30a9231d9`): the k13 working tree recorded on top of `3938c8d97142`, with fixed identity and
    date;
  * `k14-nouveau`: `k13-native` plus the 40 patches, applied with `git am --committer-date-is-author-date`.
* Both commit ids are reproducible. A re-run gives the same ids and therefore the same kernel release, as the state
  test shows.
* After every run HEAD is back on the detached `3938c8d97142` with the uncommitted k13 tree. That state is saved in
  `/build/k14/k13-state/` (99 status lines, 45 untracked files, diff sha256 `1ce27f91a413...`).
* The Kleaf `--config=local` cache is shared with k13. After a k14 build it holds k14 nouveau objects, so a later k13
  rebuild recompiles nouveau. `/build/dist` is never written.
* Optional `CONFIG_DYNAMIC_DEBUG=y` variant (`/build/dist14-dyndbg`): **not built**. It needs a config change, which
  means a full rebuild of about 2 h on 3 vCPUs. It would also overwrite the shared incremental cache for k13 and k14
  (same Kleaf target), on a builder shared with the ISO workflow. The spec makes it optional. Section 5 of
  `integration/k14-kernel.md` has the recipe.

## 4. Lapis module sources used for K-06

* `C:\GB-x86\boot\vendor_ramdisk.lz4` is the vendor ramdisk that build_esp ships (sha256
  `c7f9d49d111e785f2dca10549eba4422f6b10f4c5a969fd62cbda346bfa92018`). It holds three concatenated newc archives, and
  the third one has 59 `lib/modules/*.ko`. A plain `cpio -i` stops at the first `TRAILER!!!` and finds only
  `modules.load.recovery`.
* `/build/native/audio/vendor_dlkm_b276.img`: 276.R4, `ro.vendor_dlkm.build.id=CL3B.260622.276.R4`, 484 modules.
* `/build/native/audio/vendor_dlkm_a.img`: 271.R1, 484 modules. These are byte-identical to the 276.R4 set: same
  sha256 over all `.ko`.
* Both vendor_dlkm images are erofs; they were extracted read-only with `fsck.erofs --extract`.

To reproduce the extraction:

```sh
# first copy C:\GB-x86\boot\vendor_ramdisk.lz4 to /build/k14/lapis/
bash /build/k14/tools/extract_lapis.sh /build/k14/lapis /build/k14/lapis/vendor_ramdisk.lz4 \
  b276=/build/native/audio/vendor_dlkm_b276.img a=/build/native/audio/vendor_dlkm_a.img
```

A re-extraction gave the same module hashes as the extraction used for K-06.
