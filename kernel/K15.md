## 1. Item 3 -- the #UD VNNI emulator, three defects fixed + a counter

The k13/k14 emulator (`apply_vnni3.py`) ran its user copies (the instruction fetch and the memory operand) with
IRQs disabled, because `exc_invalid_op` enters through an interrupt gate and `handle_invalid_op()` runs before any
`cond_local_irq_enable`. It also mishandled the XSAVE init state and did not zero the destination above the vector
length. k15 (`apply_vnni4.py`) fixes all three and hardens the fetch.

### 1.1 IRQs on for the user copies

`handle_invalid_op()` now brackets the emulator with `cond_local_irq_enable(regs)` / `cond_local_irq_disable(regs)`,
the idiom `do_error_trap()` itself uses. The instruction fetch and the memory-operand copy therefore run with IRQs
enabled (as on every other user-mode trap), so a not-present page (fresh, zram or under mmap contention) is faulted
in from a sleepable context, not from atomic context. **Invariant:** every user access happens *before*
`kernel_fpu_begin()`; nothing between `kernel_fpu_begin()` and `kernel_fpu_end()` faults, sleeps or takes the
counter lock. With IRQs on, `kernel_fpu_begin()` takes `fpregs_lock()` (bh off), saves the live registers unless
`TIF_NEED_FPU_LOAD` is set, and forces a restore on return; the read-modify-write of the saved image cannot be
preempted or hit by softirq FPU use. The counter records `irqon` for every emulation whose copies ran IRQs-on; on
k15 `irqon == emulated`.

### 1.2 XSAVE init state (SSE / YMM / ZMM_Hi256) and MAXVL

A component is read or written only when its `XSTATE_BV` header bit is set:

* **SSE init state:** if the SSE bit is clear, XMM0-15 are architecturally zero while the legacy `xmm_space` buffer
  holds stale bytes. k15 zeroes the 16 XMM registers in the buffer first and only then sets the SSE bit, so no
  stale byte is committed. (k14 read the stale buffer and set the bit, corrupting all 16 XMM registers.)
* **YMM / ZMM_Hi256:** the YMM and ZMM_Hi256 bits are **never set**. When a bit is clear every upper half is
  architecturally zero, and so is the result's upper half (both inputs have zero uppers, so every product and sum
  is zero, saturating forms included). A component is written only when its bit is already set: a VEX.256 writes
  the real upper half, a VEX.128 writes zero, and the ZMM_Hi256 slot of the destination is zeroed up to MAXVL
  (bits 511:256). (k14 left VEX.128 bits 255:128 and all of 511:256 stale.) `get_xsave_addr()` is called only
  after its header bit is tested, so it never `WARN`s.

### 1.3 Hardening

* The two fixed `copy_from_user(.., 5)` + `(.., 6)` fetches are replaced by `insn_fetch_from_user()` (sleepable,
  tolerates a short read at a page end), so a valid 6-byte memory-form instruction ending right before an unmapped
  page is emulated instead of refused (the k14 11-byte over-fetch bug). Decode returns a "short" status when every
  fetched byte matched but fewer than the instruction length were fetched; that is counted in `efault`.
* Refused (SIGILL, unchanged behaviour): `!cpu_feature_enabled(X86_FEATURE_AVX)`, VEX.W1 (not AVX-VNNI), 32-bit
  user mode, a uprobe XOL slot (`uprobe_get_trap_addr(regs) != regs->ip`). A faulting memory operand still gives
  SIGILL (a documented fidelity gap; hardware would give SIGSEGV), counted in `efault`. Under single-step the
  instruction is still emulated and the missing post-instruction debug trap is a documented gap (turning it into
  SIGILL would kill a debugged process).

### 1.4 The counter -- sysfs (contract 2.2)

`arch/x86/kernel/gb_vnni_core.h` holds the pure decode / lanes / xstate-merge logic (static inline, no kernel-only
calls); traps.c includes it, and so does the host unit test. The counter is a `static` struct under a spinlock,
updated after `kernel_fpu_end()` for every emulation and every `efault`, exposed by a `kobject` created in a
`late_initcall`:

* `/sys/kernel/gb_vnni/summary` (0400): one line
  `emulated N vex128 N vex256 N word N byte N irqon N efault N sse_init N ymm_init N zmmhi N`,
  then up to 16 `comm=<comm> rip=<hex> count=<N>` lines from a 16-entry comm/RIP LRU (newest first), built on read
  under the spinlock into the sysfs page;
* `/sys/kernel/gb_vnni/reset` (0200): writing `1` clears everything;
* a new comm/RIP bucket emits one `printk_ratelimited(KERN_INFO "gb_vnni: emulating VEX AVX-VNNI for comm=%s")`
  (no RIP in kmsg).

A failure to create the node only logs; the emulator works without it. No new export, so `vmlinux.symvers` is
unchanged.

## 2. Item 10 -- i915 `gb_ignore_user_gamma` (default off)

A display parameter in `drivers/gpu/drm/i915/display/intel_display_params.{c,h}`
(`param(int, gb_ignore_user_gamma, 0, 0400)` + `intel_display_param_named(...)`), read as
`to_intel_display(state)->params.gb_ignore_user_gamma`. In `intel_crtc_copy_uapi_to_hw_state_nomodeset()` each of
the three `drm_property_replace_blob()` calls is guarded `unlikely(ig & BIT(n)) ? NULL : crtc_state->uapi.<blob>`
(bit 0 = gamma, 1 = degamma, 2 = CTM). A set bit makes i915 use a linear (NULL) blob, which stops the grey "white
veil" some panels show while userspace programs a gamma LUT. The joiner secondary copies the primary's hw state, so
it follows automatically. The diff is <= 25 lines.

Default `0` keeps the original expressions exactly, so a stock boot is byte-for-byte the old behaviour. The mode is
`0400` because display params are copied into `display->params` at probe (`intel_display_device.c:1666`), so the
value is fixed at module load. Activation (i915 is loaded by GBINIT's `busybox insmod`, which ignores
`/proc/cmdline`): only through the opt-in bring-up config (lead decision D-d): `GB_MODOPTS_i915=gb_ignore_user_gamma=3`
in `gb\gb.cfg` on the ESP, read when the entry carries `gb.overlay=1` (PIPELINE's `/gbbringup.sh`, value 0-7). There
is no kernel command line route: GBINIT forwards no `i915.*` token (verify_image V25 fails an image that does), so
typing `i915.gb_ignore_user_gamma=...` in the boot editor does nothing. `3` is the recommended
setting (Night Light off, CTM-based accessibility colour correction still working); `7` reproduces gbOS86 kernel
#29. **Applicability to the SB3 panel is INFERRED** (confirmed only on gbOS86's i915 laptop); it is default-off
precisely so it is safe to ship unused, and VMware has no i915 so the default path cannot be exercised before
hardware. i915 is `=m` and ours, so the GKI KMI and `vmlinux.symvers` are unchanged.

### KAT (the in-VM known-answer test is R-13; here: the binary and the host self-check)

* `kernel/tools/vnni_kat.c` (r2, wave 3 fix phase) -> the static x86-64 ELF `C:\GB-x86\inject\kat\vnni_kat`
  (+ `SHA256SUMS`, contract 2.7), built by the NDK r27c clang `--target=x86_64-linux-android34 -static`
  (`build_vnni_kat.sh`). Every op is an explicit byte blob assembled by GNU as (`gen_vnni_kat_ops.py` r2) and
  cross-checked by disassembly (`gen_vnni_kat_check.py`: mnemonic, length, VEX `C4` / EVEX `62` prefix, `[rsi]` /
  `[rsi+0x40]`): 392 blobs (VEX and EVEX x 4 opcodes x L 0/1 x 8 register tuples x reg/[rsi]/[rsi+64], plus 8
  init-state blobs), 0 mismatches. It compares VEX (emulated) with EVEX (native) on all 32 registers x 512 bits and
  with a scalar reference that reads the 128-byte operand buffer at the op's displacement; the SIGILL negatives; the
  6-byte `[rsi+64]` op whose `ret` is the last byte before a `PROT_NONE` page, run through a call trampoline on a
  full register file; a fresh page (mincore + `ru_minflt` proof); a `PROT_NONE` operand (SIGILL + `efault`); the
  SSE and YMM-only init states with a stale xsave buffer, where one asm blob does `vzeroall` (or `vzeroupper` + VEX.128
  loads), takes the `XGETBV(1)` snapshot, runs the op and stores all 32 registers (`SKIP sse_init`/`ymm_init` only if
  XINUSE is not 0); `2 x nproc` forked workers with a 1 ms SIGALRM that sets all 512 bits of zmm0-31; with `--all`

  active swap); and the exact counter deltas: `emulated`, `vex128`, `vex256`, `word`, `byte` and `efault` must equal
