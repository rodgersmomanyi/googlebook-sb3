## 1. 0112 -- LOW-3: the task name in `/sys/kernel/gb_vnni/summary` and the kmsg line is escaped

Unchanged from the reviewed backlog patch (its README sections 2 and 8). The comm of each comm/RIP bucket and of the
rate-limited `gb_vnni: emulating VEX AVX-VNNI for comm=` line goes through `string_escape_mem(ESCAPE_HEX | ESCAPE_NAP |
ESCAPE_APPEND, "\\=")`: printable ASCII and the blank pass unchanged except `\` and `=`, every other byte is `\xHH`. One
bucket is always one line, the format strings and the first line are unchanged, a normal name prints byte for byte as
on k15. `string_escape_mem` was already in the k15 vmlinux (no new export, no config change).

## 2. 0113 -- C-SD: the SD-card reader in the keyboard base, whichever type it is

The reader's type is still unknown (it enumerates only with a card inserted; nothing has run on the SB3 yet):

| Reader type | Driver | Before k16 | k16 |
|---|---|---|---|
| USB mass-storage class (e.g. Realtek `0bda:0316`/`0328`, any `ic08` reader) | `usb-storage` / `uas` | built in (`CONFIG_USB_STORAGE=y`, `CONFIG_USB_UAS=y`) | unchanged |
| Realtek USB vendor class, RTS5129/5139/5170/5179 (`0bda:0129`, `0139`, `0140`) | `rtsx_usb` + its mfd cell `rtsx_usb_sdmmc` | missing (k15 and lapis vendor_dlkm 276) | `=m` |
| Realtek PCIe (RTS5209 ... RTS5264, `10ec:5209` ...) | `rtsx_pci` + `rtsx_pci_sdmmc` | missing | `=m` |

`CONFIG_MMC=y` and `CONFIG_MMC_BLOCK=y` are built in, so a card shows up as `/dev/block/mmcblk0`. Left off on purpose:
`USB_STORAGE_REALTEK` (with it the built-in `usb-storage` would skip Realtek mass-storage readers and wait for a
module) and `MEMSTICK` (the SB3 slot is SD-only).

**KMI.** The KMI symbol lists (`abi_symbollist`, `abi_symbollist.raw`) are byte-identical to k15's, and every k15
export keeps its name, CRC, namespace and export type. Because the GKI build keeps the exports its own modules need
(`CONFIG_TRIM_UNUSED_KSYMS` with the in-tree modules' imports), vmlinux exports the core symbols these four drivers
import that the trimmed k15 vmlinux did not: see the acceptance K-03 below for the exact list. A driver for an MMC host
cannot be a module without them (it must register with the built-in MMC core); lapis's vendor modules are unaffected
(K-06: the same result as against k15).

**Loading (native tree only).** The four modules are in **no** load list. `stage_kernel.py` (wave 8 patch) stages them
into `inject\native\modules` with a `modules.alias` and a `modules.dep` that name only them; `build_esp.py` packs both
files into `/odm/lib/modules` with the modules. lapis's ueventd has `modalias_handling enabled`
(`/vendor/etc/ueventd/ueventd.fatcat.rc`) and its ModaliasHandler reads `/odm/lib/modules` before
`/vendor/lib/modules` (the 276 `/system/bin/init`, sha256 `9c6d33419ac64c79...`, builds `base_paths =
{"/odm/lib/modules", "/vendor/lib/modules"}` in its `modalias_handling` branch: two libc++ short strings, the first
from `.rodata` 0x28e00, the second completed by immediates; evidence `w8prep\kernel-k16\evidence\
ueventd_modalias_base_paths.txt`). When the reader appears, ueventd
loads `rtsx_usb` (its dependency `mfd-core` is lapis's first-stage module: `EEXIST`), `rtsx_usb` adds the
`rtsx_usb_sdmmc` platform device, and ueventd loads `rtsx_usb_sdmmc`. Natively both link against lapis's `mfd-core`
(K-16: the CRCs agree). The VM tree is unchanged apart from the kernel.

   the five lines) and `vmlinux.symvers` (every k15 line unchanged).

The defconfig lines sit where `savedefconfig` puts them: `w8prep\kernel-k16\tools\cfg_check.sh` reproduces k15's
`gki_defconfig` byte for byte with `make savedefconfig` (the Kleaf toolchain, a scratch `O=`), then shows the k16 file
is canonical (Kleaf refuses a non-canonical defconfig: k13's first run). An out-of-tree build of the four modules
against k15's `modules_prepare` (`tools\sym_precheck.sh`) predicted the seven new exports before the Kleaf run.

The script's tree handling has its own test (`patches\k16\tools\test_kbuild16_state.sh`, the real kbuild14/kbuild15
in test mode build the base): 34 passed, 0 failed, including an interrupted run, an interrupted `git am`, 0112/0113
