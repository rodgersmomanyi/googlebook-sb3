2. Kernel / firmware prerequisites (owned by the nouveau-policy, gb-power and k14 components)
----------------------------------------------------------------------------------------------
- nouveau.ko (CONFIG_DRM_NOUVEAU=m) + drm_exec, drm_gpuvm, gpu-sched, drm_ttm_helper. NVK needs the VM_BIND/EXEC uAPI
  (present since 6.6; 6.18.21 is fine). Nothing extra for NVK beyond that.
- GSP-RM firmware: 6.18 enables GSP on Turing by default (nvkm/subdev/gsp/tu102.c: NvGspRm defaults to true).
  570.144 primary, 535.113.01 fallback (gb.nouveau.fw=535). Without GSP NVK still works on Turing but at boot clocks.
- Module ORDER MATTERS: i915 must register its DRM device BEFORE nouveau, i.e. i915 = card0/renderD128.
  lapis' minigbm (libminigbm_gralloc.so, allocator-service.minigbm, libgbm.so) has a "nouveau" (dumb) backend
  (strings: backend_nouveau) and opens the first render node it can drive. If nouveau ever became renderD128,
  gralloc and HWC would try to use the NVIDIA GPU -> no display. nouveau is never in modules.load or modules.load.late;
  gb_nouveau.sh (component nouveau-policy) loads it after sys.boot_completed only in once/test/persist modes and checks
  that renderD128 and card0 are i915 first (INTERFACES 7.2). Patch 0004 relies on the same fact: "renderD128 is not
  mine" = "gralloc is foreign".
- Runtime PM / detach: gb_power keeps the dGPU unbound by default; with nouveau bound it locks the latch, refuses
  detach while /sys/module/nouveau/refcnt > 0 and names the holders (INTERFACES 10). Any process holding NVK at a
  forced removal would get VK_ERROR_DEVICE_LOST (or die). Acceptable for test binaries, NOT for SurfaceFlinger (4b).

3. Recommended default: option (a)
----------------------------------
Keep ANV (vulkan.intel.so) as THE system Vulkan driver (SurfaceFlinger RenderEngine/Skia-Vulkan, HWUI, ANGLE GLES).
Ship NVK only as the payload ICD for explicit users (nvk_probe, the gpu-compute service). Nothing in the boot path
loads it, so it cannot break the UI, and the dGPU stays powered off unless nouveau is enabled AND a program opens it.
Linker namespaces: /vendor/bin/* binaries run in the vendor namespace, which may dlopen /vendor/lib64/hw/* and
/odm/dgpu/* (vendor default namespace permits /odm, /vendor; 276.R4 /linkerconfig/ld.config.txt).
The ICD's NEEDED list is exactly: libhardware, liblog, libnativewindow, libsync, libm, libdl, libc (libc++ and zlib
are linked statically). Re-checked against lapis CL3B.260622.276.R4 (section 7a): every import resolves; liblog,
libnativewindow, libsync, libm, libdl, libc are LLNDK (system/etc/llndk.libraries.txt), libhardware.so is in
/vendor/lib64 (and in GraphicsEnv's formerly-VNDK-SP list for the per-app driver namespace).
Apps cannot use the payload ICD: an app's classloader namespace cannot load /vendor or /odm/dgpu, and Android's
Vulkan loader has no multi-ICD support. The per-app path is the GbGfxDriver package (option A2, gfx-driver-pkg):
an ANV-first shim that keeps HWUI on ANV and adds NVK only for the app's own instances.

4. Option (b): NVK as the system Vulkan driver (NVIDIA renders, i915 scans out) - assessment
---------------------------------------------------------------------------------------------
Mechanism would be easy (ro.hardware.vulkan=nouveau); it would NOT boot to a usable UI with NVK 26.3:

 B1 (verified in source and in the binary) NVK 26.3 does not implement
    VK_ANDROID_external_memory_android_hardware_buffer (the drm-shim run lists it as absent). SurfaceFlinger's
    Skia-Vulkan RenderEngine (lapis: debug.renderengine.vulkan=true), HWUI (ro.hwui.use_vulkan=true) and ANGLE
    (EGLImage/EGL_ANDROID_image_native_buffer, WebView/Chrome) need it, and CDD 17 C-3-1 requires it for Vulkan >= 1.1.
    Patch 0003 (8b) implements it; it compiles and the extension is advertised under the drm-shim (section 7b), but it
    is unreviewed upstream and untested on hardware.
    NOT needed for window swapchains any more, see "Android 16+ swapchain fall-through" below.
 B2 (THE swapchain blocker; NVK side verified in source, minigbm side to be measured) Buffer layouts. All gralloc
    buffers come from minigbm's i915 backend in system RAM; for GPU render/texture/composer usage minigbm picks Intel
    X/Y-tiled (or CCS) modifiers (lapis' libminigbm_gralloc.so contains Y_TILED, Y_TILED_CCS, ...). NVIDIA hardware can
    only address LINEAR or NVIDIA block-linear. Unpatched NVK aborts the process on such a buffer (0001 turns that into
    an error). Patch 0004 makes every buffer NVK allocates through gralloc LINEAR by adding a SW usage bit (upstream
    minigbm: SW usage -> LINEAR; Google's build to be confirmed, nvk_probe prints the modifier). Buffers allocated by
    others (SurfaceFlinger client targets, camera, video, ANGLE AHBs on ANV) are not affected: those still cannot be
    shared with NVK unless their producer also asks for LINEAR.
 B3 Present path: unpatched nvk_android.c QueueSignalReleaseImageANDROID does QueueWaitIdle() and returns fence -1,
    so every present stalls the CPU until the dGPU is idle. Patch 0006 returns a sync_fd instead (fallback kept).
 B4 (CORRECTED) Rendering into imported buffers: NVK renders directly into a LINEAR colour target only when every
    colour attachment of the render pass is LINEAR with base address and row stride multiples of 128 B and there is no
    depth/stencil attachment (nvk_cmd_draw.c nvk_rendering_linear(); NIL's LINEAR images are 2D, single level, single
    layer, single sample anyway). Otherwise it renders into a VRAM tiled shadow and copies back at the end of the
    render pass. That shadow was only initialised for VK_IMAGE_TILING_DRM_FORMAT_MODIFIER_EXT images
    (nvk_image.c:939-1024), but Android swapchain images are created with VK_IMAGE_TILING_OPTIMAL around a LINEAR
    gralloc buffer, so for them the fallback had a zero-sized shadow. Patch 0005 fixes that. Cost either way: the
    buffers live in Intel system RAM across the base connector's PCIe Gen3 x4 link; a 3000x2000 RGBA frame is ~24 MB
    per surface per frame (written directly, or copied from the shadow), plus sampling sysmem textures over PCIe.
 B5 Power: SF would keep the dGPU awake permanently (no D3cold), several watts more.
 B6 Detach: with SF on NVK, detaching = device lost in SF/system_server = UI crash/reboot.
 B7 Boot fragility: if nouveau/GSP fails, libvulkan has no fallback to ANV -> no RenderEngine -> no UI.
 B8 (new) HWUI needs 2 graphics queues: a17 VulkanManager.cpp:245-253 asks for a second queue in the graphics family
    and HWUI aborts without it (and on VK_ERROR_DEVICE_LOST, :486-543). NVK 26.3 exposes queue_count = 1
    (26.3.0-rc2 nvk_physical_device.c:1723). Churro patches that to 2; we do not (plan 8b 0007 "not planned"): the per-app shim
    never hands NVK to HWUI ("android framework" engine), so HWUI stays on ANV.
 Android 16+ swapchain fall-through (replaces the draft's B9, which is refuted): since android16-release libvulkan's
    getProducerUsage() falls through to vkGetSwapchainGrallocUsage*ANDROID when the AHB-typed
    vkGetPhysicalDeviceImageFormatProperties2 query fails (a17 swapchain.cpp:1764-1784 "Fall through to gralloc path
    on error"; Android 15 returned VK_ERROR_SURFACE_LOST_KHR there). lapis 276.R4 libvulkan.so carries the Android 17
    strings. So a window swapchain on NVK without AHB support is blocked by tiling (B2), not by missing AHB. NVK 26.3
    exposes no GrallocUsage3/4, so the fallback lands on GrallocUsage2 (patched by 0004). nvk_probe -t
    a17-swapchain-model reproduces exactly this sequence.
Verdict for (b): still not viable on this machine (B5-B8); the per-app experiment (gfx-driver-pkg) is the only
NVIDIA graphics path, gated (plan Phase 8 gate G0 first).

5. What nvk_probe measures (run natively; results decide whether any of this is worth pursuing)
-----------------------------------------------------------------------------------------------
  Prerequisite: nouveau loaded (gb.nouveau=test boot entry, or persist.vendor.gb.nouveau=1).
  /vendor/bin/nvk_probe -n 200 -o /data/local/tmp/nvk.ppm      (as root; or: setprop vendor.gb.nvk_probe 1 and
                                                               read /data/vendor/nvk/probe.txt)
  -t offscreen          instance/device on the GTX 1650, NAK pipeline compile, render+copy, pixel check, timing.
  -t anb-swapchain      AHB with the driver's swapchain usage | HW_COMPOSER -> prints the minigbm modifier ->
                        VkNativeBufferANDROID import. Unpatched: FAIL with I915_*_TILED (B2). With 0004 the usage
                        includes SW_WRITE_RARELY -> expected LINEAR -> PASS.
  -t anb-linear         same + CPU_READ_OFTEN (LINEAR) + CPU read-back pixel check (cross-device PRIME works).
  -t ahb-i915-readback  Phase 8 gate G0: AHB CPU_WRITE_RARELY|CPU_READ_RARELY|GPU_COLOR_OUTPUT|GPU_SAMPLED_IMAGE
                        (CPU_READ_RARELY added to the plan's usage: AHardwareBuffer_lock(CPU_READ) requires it) ->
                        NVK import -> per-pixel unique pattern (pat.frag) -> release (sync_fd with 0006) -> bit-exact
                        read-back with AHardwareBuffer_lock AND by sampling on ANV (vulkan.intel.so imports the same
                        AHB, readback.comp texelFetch()es every texel). PASS = both bit-exact.
  -t a17-swapchain-model  GPDIFP2 with the AHB handle type (expected VK_ERROR_FORMAT_NOT_SUPPORTED without 0003) ->
                        GrallocUsage4/3/2/1 like libvulkan -> allocate with SF consumer usage (COMPOSER_OVERLAY |
                        GPU_SAMPLED_IMAGE) + producer usage -> VkNativeBufferANDROID + VkSwapchainImageCreateInfoANDROID
                        -> vkAcquireImageANDROID(fd -1, fence) -> render -> vkQueueSignalReleaseImageANDROID with a wait
                        semaphore -> poll the sync_fd -> pixels checked on ANV. Must PASS with 0004 (plan 8, gate).
  -T <s> per-test watchdog (default 60 s, SIGALRM -> "TIMED OUT"), -A <icd> ANV for the read-back legs.
  Exit codes: 0 pass, 1 a test failed, 2 ICD/instance error, 3 NO_DEVICE (expected in the VMware VM).

6. Facts and limits for app developers / testers (P0-4)
--------------------------------------------------------
- Texture compression: NVK reports textureCompressionETC2 = false and ASTC only on Tegra SoCs (26.3.0-rc2
  nvk_physical_device.c:377-379, nvk_has_astc() :105-109); BC is supported.
  Many Android games and the Android Baseline profile expect ETC2/ASTC, so they will skip or reject the NVK device
  (the shim keeps ANV as device 0, so they still run, on ANV).
- Mesa options on Android: environment variables do not reach zygote-forked apps; Mesa reads them from properties
  named debug.mesa.<x> and then vendor.mesa.<x> (lower case, "_" -> "."; MESA_FOO -> mesa.foo). The bare mesa.<x>
  prefix is ignored at ANDROID_API_LEVEL >= 33 (util/os_misc.c:197-205). Examples: NVK_DEBUG ->
  debug.mesa.nvk.debug; NVK_ANB_LINEAR -> debug.mesa.nvk.anb.linear; MESA_SHADER_CACHE_DISABLE ->
  debug.mesa.shader.cache.disable.
- platform-sdk-version 35 vs 37 / android-strict: the NDK r27c sysroot tops out at API 35 (compiler target
  x86_64-linux-android35), lapis is SDK 37. -Dplatform-sdk-version only sets Mesa's ANDROID_API_LEVEL; 26.3.0-rc2 has
  no NVK/runtime/util code guarded by a level above 35 (grep 2026-10-25), so 37 changes no code today (base profile
  keeps 35 for the bit-identical NV-01 rebuild). android-strict (Mesa default true) only caps NVK at Vulkan 1.1 when
  ANDROID_API_LEVEL <= 32 (nvk_physical_device.c:69), so it has no effect at 35/37; at >= 33 it does drop the bare
  "mesa." property prefix (above). Re-check both greps on every Mesa bump (50_rebase_mesa.sh).
- Property-name length: our own properties stay <= 31 characters (INTERFACES 2.4). Mesa 26.3 itself handles long
  names (os_misc.c raises PROP_NAME_MAX to 128 at API >= 26; older Mesa cut names at 31 - Churro carries a patch for
  that). The two new Mesa options were chosen so that even the vendor.* spelling fits: vendor.mesa.nvk.anb.linear
  (26), vendor.mesa.nvk.anb.waitidle (28).
- Shader cache: compiled in (8a), but Mesa keeps the disk cache OFF on Android unless MESA_SHADER_CACHE_DISABLE=false
  (property debug.mesa.shader.cache.disable=false) and a writable MESA_SHADER_CACHE_DIR are set (disk_cache_os.c).
  The gpu-compute service must set both (integration note for component 5).

10. INTERFACES v1.2 (graphics switching, wave 1b, 2026-10-25)
-------------------------------------------------------------
10.1 NVK, patches and the payload ICD are unchanged (vulkan.nouveau.so 625314e0..., libgb_nvk.so 6bb6dc80...).
10.2 nvk_probe is now also the probe of the automatic self-test gate (decision D4, INTERFACES 25): root service
     gb_gfx_selftest runs `timeout 150 nvk_probe -t ahb-i915-readback -T 60`, then the same with
     a17-swapchain-model, on the first healthy bind per identity (build id, kernel, gfx_build_id with icd/nvk/probe
     hashes). The probe binary hash is part of that identity (probe=), so every probe rebuild re-runs the test once.
10.3 v1.2 probe changes (src/nvk_probe.c "Supervision"; README "Self-test invocations"): stop signals kill the test
     child before the probe ends, PDEATHSIG in both directions, parent-side -T deadline, "requested test not in
     this build / no test ran" is exit 1, an explicit -d/-A path that does not exist is exit 2 (no silent fallback).
     Exit codes 0/1/2/3 are otherwise unchanged. Evidence: logs/wave1b/, integration\nvk-gfxdriver.md section 7.
10.4 Per-app NVK (the shim in gfx-driver-pkg) is no longer an experiment: NVK first while vendor.gb.gfx_active is
     nvidia, for the apps that gb_power's Settings select (games + "Use NVIDIA", or all; "Always Intel" wins).
     Sections 3-6 above (option (a), facts for app developers) still hold; "ANV is device 0" is replaced by
     "NVK is device 0 when gb_power says nvidia" (gfx-driver-pkg\README.md).
