## 5. Spec questions and deviations

1. **37, not 38, stable patches.** The range v6.18.21..v6.18.57 has 38 nouveau-touching commits *including*
   "drm/client: Remove holds_console_lock". Excluding it leaves 37 (`0001`-`0037`), not `0001`-`0038` as 18.3
   says. Verified with `git log v6.18.57 -- drivers/gpu/drm/nouveau` on a kernel.org fetch; it matches the TSV row
   for row. `v6.18.58` adds no nouveau commit.
2. **Patch 0022 carries a one-line backport fix** (`kzalloc_obj(*priv, GFP_KERNEL)`). android17-6.18's `kzalloc_obj()`
   has a mandatory GFP argument; the first build failed without the fix.
3. **N1 is narrower than the plan's wording.** It skips `pci_ignore_hotplug()` only when the bridge has `_PR3` (with
   `bridge_d3`) **and** the host bridge has native PME or no native PCIe hotplug. Only then does pciehp mask its
   interrupt across D3cold; otherwise a bound GPU could be removed on a link-down. xe keeps `ignore_hotplug` on its
   _PR3 path, amdgpu dropped it (K14.md).
4. **N2 does not call `drm_dev_unplug()` from the resume callbacks.** It would deadlock under `drm_dev_enter()`
   (`nouveau_drm_postclose()`). The unplug stays first in the remove path, where nouveau already does it. N2 also
   guards system resume (`nouveau_pmops_resume`) and fails GSP-RM waits fast through a new `nvkm_device.gone` flag;
   both go beyond the plan's three functions.
5. **N3 also checks the VRAM eviction result** (runtime suspend only) and undoes the SVM/dmem/LED suspend steps on
   failure. The plan named "VRAM eviction or nvif_client_suspend" as failure sources, and 6.18 ignores the eviction
   result entirely.
6. **The optional `CONFIG_DYNAMIC_DEBUG=y` variant was not built.** It needs a full rebuild (about 2 h on 3 vCPUs) and
   would overwrite the shared incremental `--config=local` cache used by k13/k14 on a builder shared with the ISO
   workflow. Recipe for later, when the builder is otherwise idle and `/build` has at least 12 GB free:
   1. on a branch `k14-nouveau-dyndbg` from `k14-nouveau`, add `CONFIG_DYNAMIC_DEBUG=y` to
      `arch/x86/configs/gki_defconfig`;
   2. build with `--destdir=/build/dist14-dyndbg` and a different `BUILD_NUMBER`;
   3. never stage the result.
   The variant changes `.config` (and possibly vmlinux exports), so it is for debugging only.
7. **Output directory** is `/build/dist14` (INTERFACES 1.1 and 18.3), not the task text's example `/build/dist-k14`.
8. **README location.** The component's README is `C:\GB-build\kernel\patches\k14\README.md`, because the component owns
   `kbuild14_native.sh`, `patches\k14\**` and `K14.md` but not the whole `C:\GB-build\kernel\` folder.
9. **Builder scratch kept for Wave 2.** `/build/k14/` keeps:
   * `patches`, `tools`, `kbuild14_native.sh`, `k13-state` (needed by `--restore`);
   * `accept` (evidence) and `lapis` (150 MB, needed to re-run K-06; `tools/extract_lapis.sh` can recreate it).

   The kernel.org fetch, the scratch apply trees and temporary files were removed. Delete `/build/k14/lapis` after
   Wave 2 if space is short. The branches `k13-native` and `k14-nouveau` stay in `/build/gki/common` (refs only).
10. **D11's premise does not hold for this build.** k14's modules and bzImage use the same autogenerated module-signing
    certificate as k13:
    * serial `2D19D4615D376A8775241216C503DF0761081547`;
    * SHA-256 fingerprint `CB:EA:EB:8F:...:99:FC`;
    * evidence in `K-05.txt` and `K-05-k13-key.txt`.

    Kleaf's `--config=local` cache keeps `certs/signing_key.pem` between incremental builds, so a new key appears only
    with a clean cache or a sandboxed build. A mixed k13/k14 module set would therefore pass signature checks, and
    with MODVERSIONS the vermagic comparison skips the release token. Staging should still take everything from one
    build (stage_kernel does), but D11's wording ("Kleaf signs with a new autogenerated key per build") should become
    "every build *may* have its own key; always restage from one dist". Two consequences follow:
    * the plan's acceptance "every staged `.ko` signer == bzImage key" is the meaningful check;
    * verify_image (W2-07) should compare the module signer with the certificate built into the image's `vmlinuz`, not
      with a remembered key id. `k14check.py sig` shows how: certificate from `system_certificate_list` /
      `module_cert_size`, signer from the PKCS#7 SignerInfo.
11. **Hardware observability.** Suggested for W2-02 (`gb_bootlog`) and component 1's report: also capture
    `dmesg | grep -E '_OSC|pciehp'` and the three k14 messages listed in 1.5. They show on the first hardware boot
    whether N1 is active (native PME + _PR3) or whether k14 behaves like k13 there.
